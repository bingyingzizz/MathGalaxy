# 工作流：引擎开发（engine）

> 触发：渲染、布局/几何、搜索、交互、缓存、资源加载、构建性能、预计算，以及其它**非内容**的工程改动。
> 技术真源：[`PERFORMANCE.md`](../../PERFORMANCE.md)（总账 + 准入规则 §0.0 + 机器守卫不变量 §4）与 [`docs/performance-runbook.md`](../performance-runbook.md)（操作手册 4.0–4.6、验收四件套）。**本文只规定顺序与边界，不重复其细节，也不复述其中会过期的数字。**

> 布局/密度背景/超边路由的设计、产物与校验：[`docs/layout-routing.md`](../layout-routing.md)（Task 3）；回归命令 `bun tools/routecheck.mjs`。

> 节点名（标签）渲染的精确加速 / 缩放帧直画 / 懒物化：`PERFORMANCE.md` §13 与 runbook 4.4¾；回归命令 `bun tools/labelcheck.mjs`（离线对拍）+ 验收包 `_tmp/task3d-accept/`（页内探针）。

## 1. 开工前（性能敏感改动：强制）

「性能敏感」**不止 `src/core/`**：渲染（含云雾/标签/hover）、布局与预计算（`layout.js`、`layoutcache.js`、`tools/prelayout.mjs`）、图算法与数据结构（`graph.js`、`layers.js`、搜索索引）、缓存与签名、交互、资源加载与启动路径、构建关键路径。

1. **读** `PERFORMANCE.md`（至少 §0–§5、§7、§10）与 `docs/performance-runbook.md`。
2. **找回历史**：此前的优化决定与**失败的做法**（总账里每刀的「问题→改法→实测」与「必须这样不能那样」）。
3. **列出受保护的不变量与受影响子系统**（`bun tools/perfguard.mjs` 的全部断言；见 PERFORMANCE §4）。
4. **建立可比的基线**：同机、同窗口（`2536x1348`）、同 k、GPU 开（`MG_GPU=1`）；先排除两种作废环境（60Hz 档、`getImageData` 回读滞后，见 runbook 4.0）。

## 2. 实施与验证

5. **最小的连贯方案**；不重设计，不顺手重构。
6. **正确性与回归**：`bun tools/perfguard.mjs`；相关的引擎冒烟；带裁剪墨量比对；**亲眼看截图**（runbook 4.1.3）；`bun tools/searchcheck.mjs`（搜索改动）。`build 绿 ≠ 改对了`。
7. **前后实测**：**按受影响的子系统选相关基准**（拖动/缩放/渲染 → 两个仪器；启动/布局 → `layoutMs`；搜索 → `searchcheck` 与检索基准；构建关键路径 → 构建耗时；只量与改动相关的，**不为凑数把所有基准都跑一遍**），且**保持可比的测量条件**（同机、同窗口、同 k、GPU 开）。仪器：两个仪器（`_tools/_dragbench.mjs` 真鼠标 + `_tools/_chainprobe.js` 假拖动）各量一次，报 p50/p95/max 与结构指标（追赶/落洞/分配/出图率）；启动类另报 `layoutMs`。**没实测就写「未实测」**，不得写成已验证：**未实测的性能敏感改动不算「性能已验证」**，汇报里要列出**尚待完成的验证项**（哪个基准、什么条件），不得以「功能正确」代替。
8. **复查交互、边界与兼容**（缩放、拖动、触屏/手机 dpr≥2、`file://`、移动端、搜索与深链）。
9. **更新技术文档**：总账（PERFORMANCE.md）与手册对应节；区分**历史基准**与**当前实测**——历史数字保留原值，不改写成当前。

## 3. 必须保留的既有优化（不要因「更简单/更现代」去掉）

布局预计算、布局签名与稳定性、视口裁剪、LOD、位图缓存（横带切片等）、相机与缩放行为、事件处理、搜索与加载优化、perfguard。取代某个既有优化**需要证据**（前后实测）；**显著的性能权衡须先获批准**。

## 4. 红线

- ⛔ **不放宽** `perfguard` 断言、旋钮取值区间、4.2 ms/p95/max 判据来迁就退化；要改某条约束，先在 PERFORMANCE.md 给出改前/改后的实测，再改对应断言，并经批准。
- ⛔ 引擎与内容分家：不借引擎改动改数学内容；渲染改动**不得改变边的数学语义**（黑/粉/等价/类比/定义的含义与分层规则）。
- ⛔ 零依赖、经典 `<script>` + `window.MG`、`file://` 可开；不引入框架/打包器/ES module/npm 依赖。
- 单一机器的 headless 数据不能当「普适结论」；在 STATUS/总账里写明测量条件。

## 5. 验收与完成条件

- perfguard 全过（未改断言）；相关冒烟/墨量/截图已做；性能敏感改动有前后实测（或明说未实测）。
- 技术文档已更新；`bun tools/doccheck.mjs --strict` 与 `bun tools/hygiene.mjs` 无新增问题；`git status` 无意外。
- 构建产物只经 `bun tools/build.mjs` 产生（隔离副本先行）。发布不自动（`AGENTS.md` §9）。

## 6. 失败与升级

测量环境作废 → 先修环境再下结论；回归无法在不放宽守卫的前提下消除 → 退回方案并请示（性能权衡是用户的决定）；需要大改架构 → 停下请示。
