## 2. 布局 B（自由力导向）

- 起点 = `computeLayout` 摆出的星系/星团布局（确定性），然后让节点**只受数学关系**牵引：斥力 `repulsion/d³` + 近距碰撞（`minGap`）、关系弹簧（权重按边类型：定义 0.8、推出 1.5（推论 1.0）、等价 2.0、类比 0.15；超边权重摊到端点对 `w/(m−1)`；再按 `(deg_a·deg_b)^0.18` 做度数归一，抑制高度数基础概念把图拽成一团）、微弱向心、线性退火的步长上限。650 轮。
- **星团/星系只是分类元数据**：没有团心/领域心锚力，不强制成员聚成圆盘或连通；跨领域概念自然落在中间位置（`def.banach-space` 不再被限制在旧的几何区域；它的**分类没有改**）。
- 收尾：平移回原质心；按最近邻中位距离缩放回初始量级（避免只靠整体缩小就显得更紧）；70 轮成对重叠松弛保证 ≥60。
- **斥力不能截断**：实测截断半径 700 会让整体宽度偏小 16%（长程斥力合力不可忽略）。默认精确 O(n²)；`config.layout.free.cutoff` 是可选旋钮。
- **与批准的参考实验对照**（同一份图）：相似变换残差 0.001（方差比），平均/p95 推出距离 259.6/589.3 对 259.9/591.0，`def.banach-space` 位置 (114,1049) 对 (113,1045)。
- 成本（Bun，本机）：冷算 ≈28.7 s（旧布局 ≈9.2 s，自由松弛约 +19 s）。**构建期预计算是主路径**；无有效预计算时浏览器冷算会变慢（原来就是「只保证能打开」）。
- 确定性：无随机数、遍历顺序固定；两次构建 `dist/layout.json` 字节相同（已验证）。
- **增量稳定性**（删 8 个节点后重算，1728 个共有节点；位移相对宽度 ≈5100）：平均 123、中位 83、p95 331；最佳刚体对齐后仍 98；旋转 2.5°；无反射。旧布局同条件：平均 156、中位 77、p95 608、1°。结论：不比旧布局差；**没有做「用上次位置当初值」的热启动**——那会让结果依赖上一份产物而不再只由源数据决定（违背确定性），若要做需要你拍板（见 §8）。

## 3. 密度背景（B+）

- 旧做法的缺陷：星团包络/板块圆在自由布局下会被远处成员撑过无关区域。现改为局部密度 `ρ_C(x)=Σ exp(−‖x−x_i‖²/2σ²)`（板块 σ=180、星团 σ=95、大板块 σ=240，世界单位）。颜色 = 各组按纯度加权的平均；浓度 `1−exp(−κρ)` 饱和 ⇒ 重叠学科区不会无限变深；孤立成员不拉出长条。
- **标签锚点** = 「密度×√纯度」最大的像素（代表性局部峰），不是质心，所以不落在两个浓团之间的空地。区域/星团锚点在构建期算好随 `layout.json` 发出；大板块锚点依赖 `sectors.js`（构建的无头环境不载入它），运行时随纹理一起补。标签的显隐、层级、语言、避让逻辑**没改**，只换了锚点来源。
- 星团包络（`drawEnvelopes`）在密度模式下关闭：自由布局下「成员外轮廓」会圈进无关区域，归属改由密度背景表达。
- 数值核心与批准的原型**逐字节一致**（0 字节差，锚点差 0）；高斯核改为可分离并只扫每组包围盒。纹理长边 512（原 768）。
- **静态密度全部在构建期算**（`prelayout.buildDensityStatic`，≈0.2 s）：纹理压成 PNG（≈135 KB，base64 ≈180 KB）+ 区域/星团/大板块锚点，随 `layout.json` 发出并内联进单文件；签名 `densitySignature` = 布局签名 + 坐标哈希 + 密度配置；构建硬门会**重算并逐字节比对**（顺带验证确定性）。运行时只用 `Image` 异步解码（后台线程，不占主线程），结果与现算**像素级相同**（最大差 0）。运行时**没有**密度现算。
- **静态 vs 动态**：密度场与颜色混合是静态的，与主题、可见性过滤、缩放都无关（雾是世界级背景，过滤只影响节点/连线）。主题（亮/暗倍率）、缩放补偿（`fogZoomBoost`）、不透明度仍在 `draw()` 里做轻量合成，不重算任何密度场。
- 大板块锚点需要 `sectors.js`，而构建的无头环境不载入它（载入会改变布局输入），所以 `buildDensityStatic` 在隔离的 vm 里单独读它，只用于密度分组。
- 恢复路径：纹理解码失败 / 旧产物没有纹理 ⇒ 回退到现算（≈94–150 ms，控制台警告）；这不是正常生产路径。
- 旋钮：`config.background.density`（整个对象进布局签名与密度签名）。

## 4. 推出超边路由

### 4.1 范围与语义

- 只处理**强推出边**（黑 + 粉）；定义/等价/类比的算法与呈现**不动**（等价边与有「平行边让位」弓形的单前提边只作为干涉背景，用弦近似）。
- 汇合点/折点/分流点**只是几何**：不进数学图、不影响层号、没有名字。一条路由保留完整前提集合、结论、边 id、证明归属。
- 共享主干只在「**原始前提相同**」的出边之间出现；黑/粉不混；不同前提集独立证明同一结论**不会**被画成一个合取；每个共享段携带全部成员边 id（fan 组），每条边的完整路线可恢复。

### 4.2 流水线（移植自批准的 B+ 实验，改写为 JS 与空间索引）

0. **初始合流树**（`routeinit`）：对前提做紧致层级聚类（complete linkage），每个聚类节点生成有限个汇合点候选，自底向上每个子树留 2 个方案，与「全直连」「单汇合点」按 `违规数 → F=L+λD+μR(+汇合点罚) → 汇合点数` 的字典序比较。**局部凸包**：候选只取自 `S_J` 的质心/成员/到结论的凸组合，远源组限制在其质心半径内 ⇒ `J ∈ conv(S_J ∪ {T})`。与原型的区别：不再限制 n≤8 才做层级（大超边也走层级）。
1. 汇合点局部重定位；2. 共同前提的多节点分流（同色、角度接近的相邻出边共用主干再分开）；3. 重叠最重的段局部折弯（`maxBends` 上限）；4. 早合并（远源紧致组先在源侧汇合）；5. 更长的延迟分流；6. 主干继续向目标方向延长 / 嵌套分流。

每个候选必须**不增加该边的违规数与穿过其它数学节点次数**，且 D/R 不超界；打分含近平行重叠、真交叉、总长、额外路径、回头路、汇合点数。全程无随机数，遍历顺序固定。有界候选 + 空间索引，不做全子集枚举或精确 Steiner。

### 4.3 产物与失效

- `dist/layout.json` 的 `routes: {v, sig, f:[[fanTag, 根节点下标]], e:{边id:[[ax,ay,bx,by,w,flags,srcIdx,fanIdx,fanSrcIdx]]}}`：source 段的起点与 target 段的终点**不存坐标**（解码时取节点坐标，逐位等于节点）；其余坐标取 0.01。约 +137 KB（单文件 +≈170 KB）。
- **签名** `routeSignature = hash(布局签名 + 全部节点坐标哈希 + config.route + config.node)`（`MG.layoutCache.routeSignature`，唯一权威）。改了坐标/配置/内容版本/节点尺寸 ⇒ 整包作废。
- **运行时回退**：签名不符、缺失、解码失败、边已不存在 ⇒ `graph.routeData = null` ⇒ 渲染器整体回退到旧的「每条边一个汇合点」画法。冷算/localStorage 的坐标与构建期坐标不逐位相同，所以**只有预计算布局才用新路由**。
- 构建硬门（`prelayout.assertLayoutFile`）：路由签名一致 + `validateRoutes` 零错误，否则构建变红。

### 4.4 校验（`validateRoutes`，构建硬门与 `routecheck` 共用）

坐标有限、无零长段；前提集合与图一致；source 段从该节点出发、target 段落在结论上；每个前提沿**唯一链路**到达结论（无环）；每个汇合点局部凸包；fan 组 ≥2 条边、几何逐位相同、同色、起点是每个成员的前提。

## 5. 渲染 / 交互 / 导出

- **渲染**：每条路由逐段按节点屏幕半径裁剪（极小缩放下裁剪会反向 ⇒ 该段丢弃）；终端箭头与内部小箭头（放不下 <3.1px 就不画）；共享段（同 fan）只画一次，取可见成员里最亮/最粗的样式；位图烘焙、横带切片、`cullBox`、`EMPTY_GEOM` 等既有架构不变（路由与普通边走同一条绘制路径）。
- **命中检测**：点到共享主干得到 `{type:'fan', members}`（只含**可见**成员，隐藏的边不会成为候选）；只剩一个可见成员 ⇒ 普通边点击。
- **证明选择界面**（`fanpicker.js`，复用 `.floating`/`.pn-btn`，不是原型的临时弹窗）：点击即高亮这一组；列表项显示当前语言的推出名与结论名（内部 id 只在悬浮提示）；悬停/键盘聚焦预览那一条完整结构；点击打开原有证明面板；点别处/换节点/换边/Esc 关闭并还原先前焦点；Esc 只清临时状态；方向键在选项间移动；临时 fan 焦点不写入地址栏。
- **导出**：SVG/TikZ 输出实际路由（共享段只输出一次、终端带箭头、内部分段带小箭头）；子图 JSON 不含任何几何点，路由不可能被当成数学节点。

## 7. 与原型的差异与已知局限

- 原型是 Python+NumPy 的离线求解器 + 烘进 HTML 的坐标表；这里**没有搬任何坐标/路由表**，也没有任何按节点名的特例；求解器是通用 JS 实现，参数是旋钮。
- **性能验收未完成**（见 PERFORMANCE.md §11）：本机无 GPU、headless 落在 60 Hz 档，两个仪器的绝对帧时全部作废。
- 内部几何违规（如两线贴得过近）没有归零（原型同样有残余）：这是几何局限，**与语义违规分开报告**——语义违规（前提/归属/凸包/可恢复性）必须为 0（构建硬门）。
- 带弓形的单前提边（平行边让位）与等价边仍走旧画法，只作为干涉背景（弦近似）。
- 没有承诺平面性；无法画出理想路线时，回退到数学上无歧义的画法（全直连/单汇合点），而不是更短但有误导的路线。

## 8. 启动路径与冷算（谁会走到、为什么、怎么防）

正常生产启动只有一条路：**加载预计算产物**（坐标 + 路由 + 静态密度），不做力导向求解、路由优化或密度现算。`graph.layoutMode` 记录实际走了哪条：

| 入口 | `layoutMode` | 说明 |
|---|---|---|
| `dist/mathgalaxy.html`（单文件，离线 / `file://` 均可） | `pre` | 内联了与 `layout.json` 同签名的产物；构建硬门保证它存在 |
| 站点（http）：`layout.json` 由 `publish.mjs` 发布并校验 | `pre` | `index.html` 的抓取脚本先试站点根，再试 `dist/` |
| 源码 `index.html`（开发） | `cold-dev` | `contentVersion` 是 `'dev'`，签名必不匹配 ⇒ 现算（浏览器实测 ≈14 s）；预期内，加载文案写明「开发模式」 |
| localStorage 命中上次的冷算 | `cache` | 便宜，不是求解 |
| 生产产物缺失 / 过期 / 不兼容（手改、旧产物、截断） | `cold-recovery` | **不应发生**：保留冷算只为「总能打开」，但会 `console.error` 并在加载文案里明说，不再静默 |

- **没有删任何入口**：离线、开发、恢复三条都还在；变的是「不静默」与「发布前就能发现」。
- **发布前检测**（`bun tools/build.mjs` 硬门）：`layout.json` 必须存在且与当前图逐点一致；坐标 / 路由 / 静态密度都按当前坐标**重算并比对**；`dist/mathgalaxy.html` 必须内联同签名的产物且带 `routes` / `bg` / `tex`。任何一项缺失构建就失败，而不是让用户的浏览器首次打开时现算十几秒。`publish.mjs` 原有的 `layout.json` 版本/签名/计数检查未改。
- 冷算慢（Bun ≈28.7 s、浏览器 ≈14 s）是**离线计算成本**，已决定接受：保留精确 O(n²)，不做热启动（会让结果依赖历史产物，违背确定性），也不在 Task 3 里研究别的力求解器。

## 10. 视觉修正：定义线外观与平移时「端点出屏就消失」（Task 3 收口后）

**定义线外观**（诊断已对当前渲染器核实）：自由布局让定义线变短——世界长度 >1300 的占比 6.7%→0.4%、p90 1119→618、均长 −33%，原来按 1300→3400 设计的长边衰减几乎不起作用；线又短又均匀，在同一笔合并描边里糊成一片。修法只动定义线：`config.edge.defLongFade`（≈原值×0.55 的重标定：700→1900，floor 0.18）与总览档线宽 `defWidthOverview`（0.72，参考候选，不是通用常数），在 `defWidthRel`（rRel 1.35→2.8）内平滑过渡到原 `definitionWidth`，**近景与原来逐位一致**；选中/悬停不变；仍是合并描边（一帧内所有未激活定义线同宽，分组数不增加）。LOD 可见性策略不变（定义线在总览仍显示，与线上基线一致）。推出/等价/类比的样式没动。

**平移时边消失的根因**（已复现）：除几何裁剪（`polysHitView`/`cullBox`，带 140 px 余量）之外，还有一层**只看端点**的二次判断：
- 定义线（rRel≥1.35）：两端都在屏外 ⇒ 整条不画；一端在屏内 ⇒ 不透明度 ×exp(−屏幕长度/320)。实测 k=0.9：一端在屏内的 375 条平均只剩 0.35 的不透明度，两端都在屏外但弦穿过视口的 14 条被丢；k=0.45 同样。
- 推出线（rRel≥2.8）：两端都在屏外 ⇒ `off`（合流边靠 `g.trunk` 豁免）。
- 位图烘焙时这些判断用的是**烘焙画布**的端点，重烘一次就跳变。

修法：删掉这两处端点判断，线段只要几何上与可见区域相交就可见；「别让长线横穿空白」由按**世界长度**的 `edgeFade`/`defLongFade` 负责（与相机/端点位置无关）。**保留**了 `edgeInView`/`segHitsView`/`cullBox`/带裁剪、位图与 CSS transform 平移、共享主干归属、可见性过滤与 LOD；perfguard 42 条未改。位图模式下固定缩放的平移本来就不重建几何、不重算端点可见性（`EMPTY_GEOM` + 只改 transform）——问题在烘焙那一刻的端点判断，不在平移本身。

验证：实时画路径下一帧的 `quadraticCurveTo` 调用数（≈落笔的曲线数）k=0.45：1429→1788，k=0.9：960→1141；增加的是几何上进入视口（含 140 px 余量）却因端点在屏外而被旧规则丢掉的线。前后截图见 `_tmp/task3-20261125/shots/fix-*.png`。
